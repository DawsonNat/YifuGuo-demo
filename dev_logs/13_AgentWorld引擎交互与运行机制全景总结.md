# 开发日志 13：Agent World 引擎交互与运行机制全景总结

**记录时间**：2026-05-22
**目标**：针对外部系统（如 Flask Web 后端）如何与 `agent_world` 引擎交互，以及引擎内部的运转生命周期（输入 -> 运行 -> 终止 -> 输出）进行全景式的总结。

---

## 一、 外部系统如何与引擎交互？（输入层）

引擎本身是一个封闭的沙盒，外部系统（Flask）**不能直接调用 Agent 的方法**，而是必须通过以下三种标准的“输入通道”来干预世界：

1.  **剧本事件注入 (Script Event Injection)**：
    *   **机制**：通过 IPC 发送 `INJECT_SCRIPT_EVENT` 指令。
    *   **应用场景 1（玩家说话）**：利用 `DialogueInjectionEffect`，将玩家在 Web 端输入的文字，作为一条 System 级别的记忆，强行塞入目标 NPC（如 Jensen）的脑子里。
    *   **应用场景 2（剧情路由）**：利用 `StateChangeEffect`，在特定的 Turn（如 Turn 10），强行修改 NPC 的 `current_state`（心情/意图），从而改变其后续的对话生成倾向。
2.  **强制移动 (Force Move)**：
    *   **机制**：通过 IPC 发送 `MOVE_AGENT` 指令。
    *   **应用场景**：强制将某个 Agent 瞬间移动到另一个地点（触发场景切换）。
3.  **增量加载剧本 (Reload Scripts)**：
    *   **机制**：通过 IPC 发送 `RELOAD_SCRIPTS` 指令。
    *   **应用场景**：在游戏运行中途，动态追加新的预设剧本文件（如突然引入 Sam Altman 的剧情线）。

---

## 二、 引擎内部是如何运行的？（运行层与中间态）

当外部通过上述通道注入事件后，引擎的运行完全由 **Tick（时间步）** 驱动。核心调度器 `WorldStep.run_one_tick()` 会执行以下 11 步流水线：

### 1. 触发与感知阶段 (Phase A)
*   **处理注入事件**：`ScriptEngine` 捕获外部注入的事件（如玩家的话、状态改变），并应用到世界中。
*   **构建感知 (Perception)**：引擎遍历当前地点的所有 Agent。每个 Agent 的 `PerceptionBuilder` 会收集周围的环境信息、听到的对话（包括玩家刚注入的话）、收到的私聊等，组装成一段 Prompt。

### 2. 思考与动作阶段 (Phase B - 核心中间态)
*   **LLM 推理**：Agent 将感知到的 Prompt 发送给大模型（DeepSeek-V4-Pro）。
*   **中间态（Tool Call）**：大模型决定下一步动作。它可能不会立刻开口说话，而是输出一个工具调用（Tool Call）。例如，Jensen 决定调用 `send_message` 工具给 Tech VP 发私信。
*   **动作执行**：`ActionDispatcher` 解析这个工具调用，将私信写入数据库（RDC 通道），或者将面对面说话写入数据库（F2F 通道）。

### 3. 结算与时间推进 (Phase C)
*   **记忆压缩**：如果有 Agent 移动，触发 `BehaviorCompressor` 压缩其短期记忆。
*   **持久化**：将所有状态和对话刷入 `WorldDB` 和 Zep 向量库。
*   **时间推进**：全局时钟 `t += 1`。本个 Tick 结束。

## 三、 引擎运行的终止条件是什么？

这是一个极其关键的问题。因为玩家只输入了一次，但后台可能会连续跑好几个 Tick（比如 Jensen 找 VP 核实，VP 回复 Jensen）。那么引擎什么时候才会停下来，把结果返回给前端？

**引擎自动连续跑 Tick 的条件**：
1.  **有未处理的内部消息**：如果上一个 Tick 产生了未送达的私聊（RDC）或群聊（GRP）消息，引擎会自动触发下一个 Tick，让接收方醒来处理。
2.  **有预设的定时剧本**：如果 `ScriptEngine` 中有刚好在下一个 Tick 需要触发的事件。

**引擎暂停运转（终止）的条件**：
1.  **内部消息处理完毕**：所有的私聊、群聊都已经送达并被接收方处理（回复或忽略）。
2.  **NPC 对玩家做出了实质性回应**：NPC 最终调用了 `speak_to_local` 工具，在会议室里开口说话了（产生了一条 F2F 消息）。
3.  **达到最大静默阈值（防死循环）**：为了防止 NPC 们在后台无限私聊，系统通常会设置一个最大连续 Tick 数（如 5 个 Tick）。如果跑了 5 个 Tick 还没有 NPC 开口对玩家说话，引擎强制暂停。

当满足上述任一终止条件时，后台的 IPC 任务会被标记为 `COMPLETED`。

---

## 四、 引擎的输出是什么？

引擎的输出**不是直接通过 API 返回一个 JSON 字符串**。

由于引擎是异步在后台跑的，它的所有“输出”都会被**持久化到 `WorldDB`（SQLite 数据库）中**。

当 Flask 前端轮询发现任务 `COMPLETED` 时，它会去读取 `WorldDB`，提取出以下两类核心输出：
1.  **主聊天框输出 (`overhear` 表)**：提取 Tick 流转期间产生的所有 F2F 面对面消息。这就是玩家在主界面能看到的 NPC 的正式回复。
2.  **上帝视角输出 (`direct_message` 表)**：提取 Tick 流转期间产生的所有 RDC 私聊消息。这就是投资人能在右侧屏幕看到的“NPC 内部博弈过程”。

**总结**：外部系统往引擎里扔“变量（事件）”，然后手动摇动“时间摇把（Tick）”。引擎在内部闭环思考、互相通信，直到达到稳态（终止条件），最后把所有的痕迹留在数据库里，供外部系统读取展示。
