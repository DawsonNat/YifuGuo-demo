## 汇报材料正文

你好，关于我们即将用于路演的 AI 游戏 Demo，我已经完成了从剧情原型到前后端架构的全部设计。以下是详细的汇报内容：

### 一、 故事设计与游玩体验

**1. 故事背景与角色**
我们选取了《Dropout in Silicon Valley》的第五章作为 Demo 剧本。
*   **玩家**扮演一个 19 岁的辍学生，带着颠覆性的底层算法去 NVIDIA 硅谷总部拉赞助。
*   **NPC 1 (Jensen Hwang)**：NVIDIA CEO。他在会议室里和玩家面对面（F2F）交流。性格设定为傲慢、缺乏耐心、只看重真正的技术。
*   **NPC 2 (Tech VP)**：技术副总裁。他在自己的独立办公室里。他听不到玩家说话，只作为后台的技术验证者，通过私聊（RDC）接收 Jensen 的指令。

**2. 游玩形式与三屏联动 UI**
Demo 的游玩时长控制在 25-50 个回合（Turn），大约 10-15 分钟。为了最大化展示我们 Multi-Agent 引擎的技术实力，前端 UI 分为三个区域：
*   **左侧（状态面板）**：实时显示玩家的愿景（Vision）、执行力（Execution）等数值。
*   **中侧（主聊天框）**：玩家与 Jensen 的面对面对话区。
*   **右侧（上帝视角/核心卖点）**：实时滚动展示后台 NPC 之间的私聊和内心 OS。这是给投资人看的“秀肌肉”区域。

**3. 剧情是怎么推进的？（动态路由机制）**
剧情**绝不是写死的**，所有对话均由大模型（DeepSeek-V4-Pro）实时生成。我们通过“状态机”来控制大方向：
*   **Phase 1 (破冰)**：Jensen 初始状态是不耐烦的。如果玩家前 10 轮聊得太差，触发 Bad End（保安驱逐）。
*   **Phase 2 (技术审查 - 核心 Feature)**：如果玩家抛出硬核技术，Jensen 不会立刻相信。我们在他的 Prompt 里加了强制规则，他会**主动调用工具**，在后台私聊 Tech VP 去查玩家的代码。
*   **Phase 3 (态度反转 - 爽点)**：Tech VP 给出正面评价后，这个评价进入 Jensen 的记忆。此时，系统在后台**修改 Jensen 的状态（State）**为“极度兴奋”。大模型感知到状态变化，就会生成 180 度态度反转的对话（如主动提供 500 张显卡）。

## 二、 前后端架构与引擎复用设计

为了解决“大模型推理慢导致用户干等”的痛点，并完美复用现有的 `agent_world` 底层引擎，我设计了**“双段式异步 API”**架构。

**1. 玩家输入是怎么进入引擎的？（复用 ScriptEngine）**
*   玩家在前端输入一句话。
*   Flask 后端收到后，**不创建新 Agent**，而是把这句话包装成一个 `Script Event`（具体是 `DialogueInjectionEffect`），通过现有的 IPC 机制发送给后台的仿真进程。
*   后台的 `ScriptEngine` 捕获这个事件，把玩家的话像“神谕”一样直接注入到 Jensen 的耳朵里。

**2. 怎么解决用户干等的问题？（双段式 API）**
*   **第一段（极速反馈）**：Flask 收到玩家输入后，**不等待**后台引擎跑完。它立刻异步调用一次 DeepSeek，要求用一句话描写 Jensen 的动作（如“Jensen 皱了皱眉...”），并在 1 秒内返回给前端，让 UI 动起来。
*   **第二段（轮询结果）**：前端拿到即时反馈后，开始轮询 API 2。此时后台引擎正在跑 Tick，Jensen 正在思考、甚至在私聊 VP。等这一连串动作跑完，Flask 直接去查询底层的 SQLite 数据库（`WorldDB`），把主聊天记录和 NPC 私聊记录打包返回给前端。

**3. 引擎内部是怎么运行的？（Tick 流转）**
*   后台引擎是基于 **Tick（时间步）** 驱动的。
*   玩家输入一次，后台可能会跑好几个 Tick。
*   例如：Tick N（Jensen 听到玩家的话，决定私聊 VP） -> Tick N+1（VP 收到私聊，思考并回复） -> Tick N+2（Jensen 收到回复，记忆更新，开口对玩家说话）。
*   在这个过程中，我们完美复用了引擎现有的 `ActionDispatcher`（动作分发）和 `RemoteMessageBus`（远程通信总线），一行底层代码都不用改，就实现了复杂的 Multi-Agent 交互。

**总结：**
这套设计方案既保证了极佳的用户体验（无感延迟），又完美契合了现有的底层代码架构。我们通过 `ScriptEngine` 实现了剧情的动态路由，通过 `WorldDB` 和 IPC 实现了前后端的解耦。接下来，我们就可以直接按照这个蓝图开始编写代码了。

### 三、 补充说明：关于第二阶段“代码审查”的逻辑修正 (2026-05-22 晚更新)

在早期的设计中，我曾提到 Tech VP 会去“查玩家的代码”。但考虑到玩家在 Web 端实际上只能输入自然语言（Typing），不可能真的提交一份代码仓库，因此我对故事逻辑和 Prompt 进行了**极其重要的修正**，使其完全符合文字 RPG 的游玩形式：

*   **逻辑修正**：Tech VP 的审查方式从“看代码”改为了**“技术逻辑推演”**。
*   **交互表现**：
    1. 玩家在前端输入技术概念（例如：“我用了一种新型的稀疏注意力机制，能降低 90% 显存”）。
    2. Jensen 听到后，私聊 Tech VP：“这小子说他的稀疏注意力机制能降低 90% 显存，逻辑上行得通吗？”
    3. Tech VP 收到私信后，由于无法直接看到代码，他会利用自己作为顶尖极客的直觉，**根据 Jensen 转述的技术概念进行逻辑推演**。
    4. Tech VP 回复 Jensen：“虽然没看到代码，但如果他真的解决了哈希碰撞问题，这个底层逻辑是个天才设计，值得赌一把。”
*   **Prompt 约束**：在 `dev_docs/3_prompt_management.md` 中，我已经明确将这条规则写入了 Tech VP 的 `behavior_hint` 中，强制要求大模型根据玩家抛出的“概念”进行合理的脑补和推演，而不是去索要真实的代码。

这样修改后，整个故事的逻辑就完全自洽了，玩家只需通过“画大饼”和“抛概念”就能顺利推进剧情。

### 四、 补充说明：关于地点移动 (Move) 的引擎支持与未来扩展 (2026-05-22 晚更新)

虽然我们目前选取的《第五章：Jensen Hwang 的皮衣和 GPU 圣杯》是一个**密闭空间谈判**（玩家和 Jensen 始终在会议室，Tech VP 始终在办公室），剧情本身不涉及地点的物理移动，但底层 `agent_world` 引擎是**完全支持地点移动**的。

如果后续我们需要扩展剧本（例如：谈判破裂，玩家被保安赶出大楼；或者谈判成功，Jensen 邀请玩家去他的私人车库看原型机），引擎已经提供了完备的机制：

1.  **Agent 主动移动 (`request_move`)**：
    *   引擎的 `dynamic_tools.py` 中内置了 `request_move` 工具。
    *   大模型可以根据剧情需要，主动调用此工具请求移动到另一个 `place_id`。
    *   `ActionDispatcher` 会将此请求放入 `pending_moves` 队列，并在 Tick 结尾统一结算，更新 `PlaceStore` 中的位置映射。
2.  **剧本强制移动 (`MoveEffect`)**：
    *   `ScriptEngine` 提供了 `MoveEffect` 效果器。
    *   我们可以通过 API 注入一个事件，强制将某个 Agent（或玩家）瞬间移动到指定地点。
3.  **记忆压缩联动 (`BehaviorCompressor`)**：
    *   当 Agent 发生移动时，引擎会自动触发 `BehaviorCompressor.on_move` 钩子。
    *   它会将 Agent 在上一个地点发生的所有琐碎动作，调用大模型压缩成 1-3 句话的摘要，存入 Zep 向量库，从而完美实现“场景切换时的记忆归档”。

因此，目前的单场景设计是为了聚焦核心矛盾和路演的紧凑性，但底层架构已经为未来的多场景、大地图探索做好了 100% 的准备。
