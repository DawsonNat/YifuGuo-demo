# 开发日志 06：动态路由机制与非写死剧情的结合逻辑

**记录时间**：2026-05-22

针对“剧情是否是写死的”以及“路由节点如何体现”的疑问，现将 `agent_world` 引擎中高自由度对话与可控叙事的结合逻辑进行详细梳理，以指导后续的开发。

---

## 1. 核心澄清：剧情绝对不是写死的
如果剧情是写死的，就失去了使用大模型（LLM）和 Multi-Agent 引擎的意义。在我们的设计中，**Agent 的每一句话都是由 LLM 实时生成的**。

*   **高自由度的玩家输入**：玩家可以输入任何内容（聊技术、聊商业、甚至聊家常）。
*   **动态的 Agent 反应**：Jensen Agent 会将玩家的话连同自身的性格 Prompt 发给大模型，大模型根据当前语境**实时生成**回复。
*   **动态的 NPC 内部交互（核心 Feature）**：Jensen 发给 Tech VP 的私聊内容也是**非写死**的。如果玩家吹嘘“渲染速度”，Jensen 的私聊就会是“查查他的渲染算法”；如果玩家吹嘘“商业模式”，Jensen 的私聊就会是“查查他的用户数据”。这一切完全取决于玩家的实时输入。

## 2. 路由节点在哪里？如何体现？
如果完全放任 LLM 自由发挥，游戏可能永远无法推进，或者偏离路演演示的主题。因此，我们需要在特定的 **Turn 阈值**（如 Turn 10、Turn 25）设置**路由节点（Checkpoints）**。

这些节点在技术实现上，体现为**后台状态机对 Agent 内部状态（State/Prompt）的强制干预与更新**。

### 案例拆解：路由节点如何引导剧情走向

*   **【路由节点 A】 (Turn 10 判定点)**：
    *   *后台动作*：系统检查玩家的 `Vision` 数值。
    *   *分支 1 (数值不达标)*：系统触发强制事件（Script Event），结束游戏。
    *   *分支 2 (数值达标)*：系统**修改 Jensen 的内部状态（State）**。将其 Prompt 中的目标从 `{"goal": "赶走他"}` 修改为 `{"goal": "验证他的技术"}`。
    *   *结果*：状态修改后，大模型在接下来的对话中，自然会生成更认真、更深入探讨技术的回复。剧情被平滑地“路由”到了下一阶段。

*   **【路由节点 B】 (Tech VP 给出评价后)**：
    *   *后台动作*：系统监控到 Tech VP 给出了正面评价，且该评价已存入 Jensen 的记忆。
    *   *状态更新*：系统再次修改 Jensen 的状态为 `{"mood": "excited", "goal": "拿下这个项目"}`。
    *   *结果*：大模型感知到这个强烈的状态变化，就会生成“态度 180 度反转”的爽点对话（如主动提出给予算力支持）。

## 3. 总结
**剧情内容是 LLM 实时生成的（保证了高自由度和沉浸感），但剧情的阶段性走向是由后台的路由节点通过修改 Agent 的内部状态来把控的（保证了强叙事性和路演效果）。**

这种“动态路由机制”完美兼顾了 AI 的生成能力与游戏设计的可控性，是我们 Web 端 Demo 成功的关键。
